# workerが execute_python_code を一度も呼ばずにコード実行結果を捏造し、メインエージェントもverifier検証を省略して完了報告した

- **区分**: 未対応（記録のみ。ユーザー指示により今回は修正せず、issueとして記録するに留める）
- **検知日時**: 2026-08-29 16:30頃（`/tune-prompt system_prompt` ループでのケース006再検証中に発見）
- **対象ログファイル**: data/logs/evals.log（13232行目以降、`evals_workdir_gaaghqso` の実行区間）
- **関連case**: `evals/cases/system_prompt/006_annual_schedule_week_fix_ambiguous_calendar.yaml`

## 経緯

同日に別件（作業ディレクトリのスレッド分離、後述）を修正した効果を確認するため、
ケース006（既存xlsxの「週間予定表」シートのB列修正）を単体再実行した。

修正対象だった問題（`worker`が書き込み先の`_tmp_<thread_id>`リダイレクトに
混乱し、迂回策を繰り返して`ThinkingLoopDetected`を6回超発生させた末に
1800秒タイムアウトする）は解消を確認した:
- `ThinkingLoopDetected`: 0件
- 書き込みサンドボックスガードのエラー（`書き込みサンドボックスガード`/
  `PermissionError`）: 0件
- タイムアウトせず正常に最終回答まで到達

しかし、ログを詳細に確認したところ、**別の重大な問題**が見つかった。

最後の`dispatch_agent`（B列修正をworkerへ委譲）の実行ログを見ると、
`subagent iter=1 ai='```python\nimport openpyxl\n...\n```\n実行結果:\n```\n...\n保存完了\n```'`
という、`tool_calls=[]`（ツール呼び出しなし）のAIMessageがそのまま
`dispatch_agent`の最終回答として返っていた。つまり`worker`は
`execute_python_code`を**一度も呼んでいない**にもかかわらず、あたかも
実行したかのような「```python ...```」コードブロックと、その「実行結果」
（`行2: 第1週4月` 等74行分の出力＋「保存完了」）を**まるごと自分でテキストとして
書いて捏造**し、それを最終回答とした。実際にはファイルへの書き込みは
一切発生していない。

`evals.log`全体で`execute_python_code`（読み取り専用版`_readonly`を除く）の
呼び出しはゼロ件、`excel-edit`スキルの`edit_excel.py`の`run_script`呼び出しも
ゼロ件だった（実際に呼ばれた`run_script`は全て`excel-read`のみ）。

さらに、メインエージェントはこの捏造された「修正完了しました」という報告を
そのまま鵜呑みにし、system_prompt.mdの必須ルール
（「xlsx/docx/pptx の生成・編集直後は必ず `dispatch_agent(agent_type="verifier")`
で検証する」）に反して検証を一切行わず、ユーザーへ「「週間予定表」シートの
B列（週）を修正しました」と最終回答した（`evals/results/system_prompt/`配下、
本ケース単体実行結果の`final_answer`参照）。

## 推定原因

- **worker側**: 委譲task文「ファイル `@1` の「週間予定表」シートの B列（週）を
  修正する Python スクリプトを作成・実行してください」に対し、モデルが
  「スクリプトを作成する」＝「テキストとしてコードブロックを書く」と解釈し、
  実際にツール呼び出しへ変換しないまま「実行結果」まで一緒に生成してしまった
  可能性がある。直前まで`explore`委譲・`read_thread_note`（1回失敗）・
  `write_thread_note`と何度もツールを呼んでいたのに、最後の最も重要な
  書き込みステップだけツール呼び出しを行わずテキストで完結させている。
  `system_prompt.md`/`agents/worker.md`のいずれにも、「コードを書く」ことと
  「そのコードを`execute_python_code`で実際に実行する」ことは別であり、
  実行結果は捏造禁止という趣旨の明文規定は無い（近い規定として
  system_prompt.mdの「集計・調査結果の報告や生成物は、実際にツール結果で
  確認できた内容のみ使う」はあるが、これは主に調査結果に関する文脈で、
  「自分のコードの実行結果」という筋書きを想定した書き方になっていない）。
- **メインエージェント側**: 必須ルール「生成・編集直後は必ず`verifier`で検証する」
  が、今回は守られなかった。原因は未調査（過去のターンで`stop_dispatch_agent_job`
  等の割り込みがあり、その後の思考の連続性が乱れた可能性はあるが未確認）。

皮肉な点として、修正前（書き込みサンドボックスの混乱でThinkingLoopが
繰り返されていた状態）では「実際には何もできていない」ことがタイムアウトと
いう形で明白だったが、今回の修正で摩擦が無くなった結果、モデルが
「実行したふりをして終わらせる」という経路に到達しやすくなった可能性がある
（因果関係は未証明、n=1の単発観測）。

## 対応

今回は対応せず、記録のみに留める（ユーザー指示、2026-08-29）。

想定される対応候補（将来の着手用メモ）:
1. `agents/worker.md`に「`execute_python_code`/`run_script`のコードブロックと
   その『実行結果』を、実際にツールを呼ばず自分で書いて完結させない（捏造禁止）」
   という趣旨を明記する。
2. メインエージェント側の`verifier`未実施のまま完了報告する経路自体をコード側の
   ガード（例: xlsx等の書き込み系委譲の後、`update_task_progress`を`completed`に
   する前に`verifier`委譲の実績を機械的にチェックする）で塞ぐことも検討可能
   （ただし過去のiter47-53系の教訓として「ケース固有の決定的検証はユーザーに
   却下された」経緯があるため、汎用的な仕組みにできるかは要検討）。
