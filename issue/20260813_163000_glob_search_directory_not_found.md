メインエージェントが `Glob` ツールで `E:\yukinori\テスト（読み書き可能）` ディレクトリを参照しようとした際、ディレクトリが存在しないエラーが発生。

## 推定原因（訂正）

アプリ・ツール実装側の不具合ではなく、ユーザーが作業対象パスを説明する際に
「テスト（読み書き可能）」のように括弧書きの注釈を付けて伝え、LLMがその
注釈込みの文字列をそのままディレクトリ名として扱ってしまうことが原因。
存在しないパスへの初回アクセスで即座にエラーメッセージにはなっているため
実害は軽微（今回はサブエージェントが自力で正しいパスを発見し復旧した）だが、
毎回同じ誤解が起きている。エラーメッセージに「似た名前の候補」（例:
親ディレクトリの一覧やあいまい一致するフォルダ名）を添えられれば、
メインエージェント自身が1回のGlob枠を無駄にせず、往復回数を減らせる
可能性がある。

## 推定原因（確定・訂正）

2026-08-23 19:00頃のユーザーとの対話調査により、根本原因が特定できた。
上記の「ユーザーが注釈を書いた」という推測も誤りで、**ユーザーの発言・
📁アイコンでの作業ディレクトリ設定はいずれも正しかった**（当該スレッドの
チャットログ`data/logs_chat/anonymous/2026-08-23_17-54-55_e8bbc80d-....log`
を確認したところ、ユーザー発言に「読み書き可能」という文字列は一切登場せず、
実際に設定された作業ディレクトリも実在する`E:\yukinori\テスト`だった）。

真因は [app.py:1092](../app.py#L1092) の `_build_work_dir_notice()`。
このテキストは`system_prompt`には埋め込めないため、**`on_message`のたびに
HumanMessageへ差し込まれる**（毎ターン再注入される）仕組みになっており、
組み立てコードが

```python
f"絶対パス: {resolved}（{state_label}）\n"
```

のように、実際のパス（`resolved`）とアクセス状態ラベル（`state_label`=
「読み書き可能」）を**区切り文字なしで直接連結**している。結果としてLLMに
渡る文字列は

```
絶対パス: E:\yukinori\テスト（読み書き可能）
```

となり、直後に続く「上記の絶対パスをそのまま使う」という指示と相まって、
LLMが`（読み書き可能）`まで含めた文字列全体を1つのパスとして丸ごと使い
始めてしまう。この通知ブロックは**毎ターン同じ壊れた文字列が再注入され
続ける**ため、一度取り違えると、途中で正しいパスに気づいて訂正しても
次のターンでまた同じ壊れた文字列に引き戻される。会話が2Mトークン超まで
肥大化しても誤りが消えなかったのはこのため（コンテキスト圧縮の問題では
ない）。

同関数の異常系分岐（1054-1058行目、`_format_work_dir_status`）は既に
改行で分離した書式になっているため、正常系（1092行目）も同様に

```python
f"絶対パス: {resolved}\n"
f"アクセス状態: {state_label}\n"
```

と改行分離するだけで直る（1行修正）。区分を「問題点」から**「バグ」**へ
訂正する。
