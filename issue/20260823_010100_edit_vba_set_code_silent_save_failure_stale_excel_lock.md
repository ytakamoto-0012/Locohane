# edit_vba.py: 既存Excelプロセスがファイルを開いたままだとsset_codeが成功を報告するのに保存されない（サイレントなデータ消失）

- **区分**: バグ → 修正済み
- **検知日時**: 2026-08-23 01:01:00
- **対象ログファイル**: data/logs/app_20260823_002537.log

## 経緯

excel-vbaマクロブック作成タスク（再起動後）で、`edit_vba.py`の`set_code`
（CSVインポート・月別集計・グラフ更新用のVBAマクロをModule1へ書き込み）を
`run_script`経由で実行したところ、**終了コード0・`applied_ops: 1`で成功を
報告した**にもかかわらず、実際には対象ファイルの内容が一切更新されて
いなかった。

サブエージェント自身が`read_vba.py`で確認し、書き込み後も`code_length`が
書き込み前と同じ`9258`のままであることに気づき、約13分間（00:53〜01:14頃）
にわたり自己デバッグ（LLM応答ループ検知が発動するほど長時間の推論）を
続けたが、原因（Excelプロセスの多重ロック）には気づけなかった。

こちらで直接検証したところ、以下が確認できた：

1. `E:\yukinori\vba-test\収支計算表.xlsm`は`00:38:40.740909800`を最後に
   更新されておらず、`00:53:14`に作成されたバックアップファイル
   （`収支計算表.bak_20260823_005314.xlsm`、37165バイト）と**バイト単位で
   同一サイズ・同一タイムスタンプ**だった（`diff`でも実際に同一内容と
   確認）。つまり`00:53:13`の`edit_vba.py`呼び出しは「バックアップを取って
   から`workbook.Save()`」という手順を正常終了したと報告したが、ライブ
   ファイルには何も書き込まれていなかった。
2. 同ディレクトリに`~$収支計算表.xlsm`（Excel自身が生成するロックマーカー
   ファイル）が`00:40:34`から存在し続けていた（本来この現象が起きた
   `00:53:13`より前から存在）。`edit_vba.py`独自のPIDロック追跡ファイル
   （`収支計算表.vba_pid`）は存在しなかった（サブエージェント自身が
   `00:55:07`に確認済み）ため、**このロックは`edit_vba.py`自身が起動した
   自動化用Excelプロセスによるものではない**（`edit_vba.py`は起動直後に
   必ず`record_excel_pid`でPIDファイルへ記録するため）。
3. `tasklist`で`EXCEL.EXE`（PID 24132）が実際に稼働中であることを確認した
   （後に自然終了、またはユーザー操作で終了したとみられ、ロック解消後の
   `01:13`〜`01:14`頃の書き込みからは正常にファイルサイズが変化し始めた）。

## 推定原因

`E:\yukinori\vba-test\収支計算表.xlsm`を**別のExcelプロセス（出所未特定、
`edit_vba.py`自身のPIDトラッキング対象外）がロック中**の状態で、
`edit_vba.py`が`win32.DispatchEx("Excel.Application")`で新規に起動した
別インスタンスから`excel.Workbooks.Open(...)`→（ops適用）→
`workbook.Save()`を呼ぶと、既存ロックとの競合により保存が実際には
行われない（あるいは読み取り専用として開かれ、`DisplayAlerts = False`が
本来出るはずの警告ダイアログ・例外も抑制してしまい、`Save()`が例外を
投げずに静かに失敗する）とみられる。`edit_vba.py`側は`workbook.Save()`の
戻り値やその後のファイル状態を一切検証しておらず（`edit_vba.py:126-138`）、
COM呼び出しが例外を投げなければ無条件に成功として`applied_ops`を返す。

これにより、ユーザー（LLM含む）から見ると「成功と報告されたのにファイルが
更新されない」という、原因の特定が極めて困難な状態になる。今回はLLMが
13分・複数回のループ検知を経てもコード上の原因（Excelプロセスの多重
ロック）には辿り着けなかった。

なお、このロックを作った元のExcelプロセスの出所は本ログ範囲からは
特定できなかった（`render_excel.py`/`recalc_excel.py`の呼び出しは同期間に
無く、`edit_vba.py`自身のPIDファイルにも記録が無い。並行実行されていた
可能性のあるworker/verifierサブエージェントが別のCOMインスタンスを開いた
まま終了した、または前回セッション由来の残留プロセスである可能性が
考えられるが未検証）。

## 推奨対応（未実装）

`edit_vba.py`の`workbook.Save()`（`edit_vba.py:129,131`）の直後に、
保存が実際に反映されたことを検証する処理を追加する案が考えられる。例:
- `workbook.Saved`プロパティを確認する
- 保存直前後で対象ファイルの`mtime`/サイズが実際に変化したことを確認し、
  変化していなければ「別プロセスが対象ファイルを開いている可能性が
  あります」という具体的なエラーメッセージで失敗を報告する

これにより、今回のような「成功と報告されたのに実は保存されていない」
サイレント失敗を防ぎ、原因調査に要した時間（13分・ループ検知含む）を
大幅に削減できる可能性がある。

## 追記（2026-08-23 01:15）— LLMがガイダンスに反しEXCEL.EXEを無差別taskkillし、これが実際にロック解消の直接原因だった

この行き詰まりの最中（01:12:58〜01:14:35）、サブエージェントが
`execute_python_code`経由で（まず`psutil`を試みたが未導入で
`ModuleNotFoundError`、`tasklist`/`taskkill`直接呼び出しへ切替え）
最終的に以下を実行した。

```python
subprocess.run(["taskkill", "/F", "/FI", "IMAGENAME eq EXCEL.EXE"], ...)
```

これは`skills/excel-vba-edit/SKILL.md`が明記しているガイダンス
（「対象は`edit_vba.py`が専用に起動した`Visible=False`の非表示プロセスのみで、
`tasklist`で見える無関係なEXCEL.EXEまでは終了しない」）に反し、**PIDを
指定せずイメージ名だけで全EXCEL.EXEを無差別に強制終了**するものだった。

01:13:04の1回目の実行で`tasklist`は`EXCEL.EXE PID 24132`を1件検出し、
続く`taskkill`が`成功: PID 24132 のプロセスは強制終了されました`を返した
（こちらが直接`tasklist`で確認したのも同じPID 24132で、本issueの原因と
なっていたロックそのものだったと確認済み）。01:14:35の2回目の実行時は
既に対象が無く`指定された条件のタスクは実行されていません`だった。
**この無差別killが実際にロックを解消し、以降`set_code`の保存が正常に
機能し始めた**（01:15:41、workerサブエージェントが
`Module1コード長: 9258 → 11369文字`を確認）。

結果としては実害が無く問題解決に繋がったが、もしこの時点でユーザーが
別のExcelウィンドウを対話的に開いていた場合、未保存の作業を巻き込んで
強制終了していた可能性がある点は変わらない。`.vba_pid`ファイルはこの時点
でも存在しなかった（00:55:07に確認済み）ため、LLMは「PID指定で終了する」
という正しい手順を実行しようにも対象PIDを特定できず、ガイダンスを守れない
まま無差別killへ踏み込んだとみられる。SKILL.mdの記述はプロンプトレベルの
注意喚起のみで、`execute_python_code`経由の任意コード実行に対する技術的な
強制力（例: `/FI "IMAGENAME eq EXCEL.EXE"`のような無差別フィルタを検出して
拒否する等）は無く、今回はたまたま無害だったが再発時に実害が出るリスクが
残っている。

対応は見送る（`execute_python_code`は汎用のPythonコード実行ツールであり、
`run_macro`のような特定の危険パターンへの静的チェックを機械的に一般化
するのは困難）。まずは事例として記録し、再発時に頻度・実害を見て判断する。

## 対応（実装済み・2026-08-23）

ユーザーから「PID記録によるLLM自己回復手段は過去に一度実装済みなのに機能
していない」「低パラメータモデル向けであることを意識する」「PIDトラッキングは
`_tmp_<thread_id>`に記録し、そこにあるもののみを操作対象とするサンドボックス化が
必須」という指摘を受け、根本原因の調査（Explore agent 2件）を経て以下を実装した。

**根本原因（コード確認済み）**: `edit_vba.py`の`finally`節が`workbook.Close()`/
`excel.Quit()`を例外を握りつぶした状態で試みた**直後に無条件で**
`release_excel_pid()`を呼んでいた。Close/Quitが例外を出さないことと実際に
OSプロセスが終了したことは別物で、実プロセスの生存確認を一切行っていな
かったため、Quit()が実効を持たなくてもPID記録だけが消え、以後追跡不能に
なっていた。

**実装内容**:
1. `skills/office_shared/excel_common.py`: PID記録先を対象ファイルの隣
   （ユーザーの作業ディレクトリ）から、自セッション専用サンドボックス
   `_tmp_<thread_id>/excel_locks/pids.json`へ移した（`path_memory.exec_tmp_dir()`
   を再利用、他セッションから読み取り不可・保持日数ベースで自動削除）。
2. `is_process_running`/`wait_for_process_exit`を新設し、`Close()`/`Quit()`
   試行後に実際にプロセスが終了したことを確認できた場合のみレジストリから
   除去するよう変更（生存していれば記録を残す）。
3. `terminate_tracked_processes()`を新設。自セッションのレジストリに記録
   されたPIDのみを対象に、`taskkill`のようなシェルコマンドやイメージ名
   フィルタを一切使わず`TerminateProcess`で直接終了する。LLMがPID番号や
   終了条件を自分で組み立てる余地を無くす設計（低パラメータモデルは
   プローズの禁止事項を確実に守れないため、判断自体をコード側へ移した）。
   `edit_vba.py --recover-locks`（PID番号を一切受け取らない専用CLIモード）
   として公開し、`recalc_excel.py`にも同様に追加。excel-render/pptx-render/
   docx-renderの共通COM起動処理にも同じ記録・条件付き解放を追加（これらは
   `record_excel_pid`/`release_excel_pid`を一切呼んでいなかった追跡対象外の
   COMプロセス発生源だった）。
4. `edit_vba.py`にSave直後のmtime検証を追加。保存が実際にファイルへ反映
   されたか確認し、変化していなければ「別プロセスがロックしている可能性」
   という明確なエラーで失敗を報告する（対症療法・独立した防御層）。
5. `system_prompt/subagent_common.md`・`system_prompt/system_prompt.md`に
   「OSプロセスを自分で`taskkill`しない、専用の回収コマンドを使う」という
   全サブエージェント・メインエージェント共通のガイダンスを追加（従来は
   `skills/excel-vba-edit/SKILL.md`にしか無く、スキルを問わず適用される
   安全原則になっていなかった）。

テスト: `tests/test_excel_vba_edit_pid_recovery.py`を新方式に合わせて全面
書き換え（19件）、`tests/test_excel_vba_edit_save_verification_and_recover_locks.py`
（mtime検証・`--recover-locks`CLI、7件）を新規追加。加えて実Excelプロセスに
対する手動検証（起動→レジストリ記録→`terminate_tracked_processes`で実際に
終了・レジストリから除去されることを確認）も実施済み。`pytest tests/`
410件全通過。

## ユーザー回答

「低パラメータモデル向けであることを意識して。PIDのトラッキングは
`_tmp_{thread_id}`に記録して、そこにあるもののみを操作対象とするなど
サンドボックス化が必須」（2026-08-23）。→ 上記の通り対応済み。
