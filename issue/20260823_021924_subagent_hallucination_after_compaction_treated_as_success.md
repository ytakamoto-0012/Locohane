# サブエージェントが会話圧縮直後に無関係な内容（1+1=2等）を幻覚し、dispatch_agentが正常完了として扱い実データ移行が失われた

- **区分**: バグ → 修正済み
- **検知日時**: 2026-08-23 02:19:24〜02:20:05
- **対象ログファイル**: data/logs/app_20260823_002537.log

## 経緯

excel-vbaマクロブック作成タスク中、`収支計算表.xlsm`のVBAプロジェクトが
失われていたため（別issue参照候補、本ログ範囲からは直接の原因は未特定）、
workerサブエージェントが新規xlsmを作り既存データを移行する作業を実行して
いた（iter=1〜34）。iter=34で`取引明細`シートのデータをops化する
`execute_python_code`を実行した直後、以下が発生した。

1. `02:19:24,442` サブエージェントの会話履歴圧縮が実行された
   （`会話履歴を圧縮しました (iter=34)`）。
2. 同時刻、トークン使用量がソフト閾値(81920/実測99114)に達したため、
   「これ以上ツール呼び出しを追加せず、次の応答でこれまでに分かったことと
   未処理の残りをまとめて回答してください」という注意メッセージが注入
   された。
3. `02:20:05,109` 次のLLM応答（iter=35、これが最終応答）が、
   **タスクと一切無関係な内容**を返した:
   ```
   content='1. 1+1=**2**\n2. 1+2=**3**\n3. 1+3=**4**'
   reasoning_content='ユーザーは私の思考過程を非表示にしたいと考えている...
   ユーザーの質問を再確認すると：
   1. 1+1=？
   2. 1+2=？
   3. 1+3=？
   ...'
   ```
   `reasoning_content`を見ると、モデルは「ユーザーが1+1=?等の単純な算数を
   尋ねている」と**存在しない会話を幻覚**していた（実際の会話にこのような
   やり取りは一切無い）。
4. `tool_calls=[]`（空）だったため、`dispatch_agent`はこれを
   「`dispatch_agent 正常終了: 35回で完了`」として**正常な最終回答扱い**で
   処理を終えた。
5. 呼び出し元（メインエージェント）はこの幻覚した最終応答を受け取り、
   `02:20:58`頃「workerの応答が異常だったため、再度修復作業を行う必要が
   あります」と自ら気づいて修復を試みたが、`02:22:53`時点で
   「VBA Module1が存在しない」「月別収支シートの集計値が全てnull」という
   状態を確認しており、**workerが本来行うはずだったデータ移行作業は
   実質的に失われていた**。

## 推定原因

未検証。`会話履歴を圧縮しました`（圧縮処理自体は成功）とトークン閾値
注意メッセージの注入が同時刻に発生した直後の1手で、モデルが直前の会話
文脈から完全に外れた内容（存在しない「1+1=?」という質問への回答）を
幻覚した。可能性としては：
- 圧縮によって渡されたプロンプト構造（要約＋直近数件のみ）が、モデルが
  普段見慣れた構造と大きく異なり、何らかの理由でモデルの応答生成が
  破綻した（ローカルllama-server側のプロンプトテンプレート処理や
  KV-cache関連の問題の可能性はあるが未検証）。
- 圧縮後のプロンプトに、たまたま無関係なサンプル/テンプレート文言が
  混入した可能性（未検証、`context_compaction.py`の要約プロンプト・
  圧縮後のメッセージ組み立てロジックを要調査）。

いずれにせよ、**`dispatch_agent`側は最終応答の`tool_calls`が空であること
だけを「正常完了」の判定基準にしており、応答内容がタスクと整合しているか
の妥当性チェックが一切無い**ため、今回のような完全に無関係な幻覚応答でも
「35回で完了」という成功扱いになり、実際にはタスク（データ移行）が
未完了のまま静かに握りつぶされた。これが本件の実害（VBAプロジェクト
喪失・集計値null）に直結した。

## 推奨対応（未実装）

- `dispatch_agent`の最終応答受け入れ時に、直前のタスク文脈との最低限の
  整合性チェック（例: 直前のツール呼び出しで進行中だった作業に一切触れて
  いない極端に短い/無関係な最終応答を検知したら、その回で打ち切らず
  最終応答としては受理しつつ呼び出し元に「応答が短い/文脈から外れている
  可能性がある」旨の警告を添える）を検討する余地がある。
- 会話圧縮直後・トークン閾値注意メッセージ注入直後の1手を対象に、応答が
  極端に短い（例: 50文字未満）かつ`tool_calls`が空の場合は自動的に1回
  だけ再試行する、という安全策も考えられる。

今回はコード修正を行わず、まず事例として記録する（発生頻度が低く、
今回のトリガー条件（圧縮＋トークン閾値注意の同時発生）を確実に再現できて
いないため、対策の的を絞れていない）。

## 対応（実装済み・2026-08-23）

`src/subagent.py`の`run_subagent`に、会話圧縮成功直後・トークン閾値注意
メッセージ注入直後の1手に限り、`tool_calls`が空かつ本文が80文字未満の
最終応答を「疑わしい」とみなし、1回だけ`HumanMessage`でやり直しを促して
再試行するガードを追加した（`hallucination_retry_used`フラグにより2回目
以降は無限リトライせず受理する。圧縮/nudgeが起きていない通常時・十分な
長さの正当な最終応答には一切影響しない）。

テスト: `tests/test_subagent_post_compaction_hallucination_guard.py`を
新規追加（4件）: (a) 圧縮直後の短い幻覚応答が1回だけ再試行されること、
(b) 2回目も短ければそのまま受理し無限リトライしないこと、(c) 圧縮/nudgeが
起きていない通常時は同じ短い応答でも即座に受理されること、(d) 圧縮直後でも
十分な長さの正当な応答は再試行なしで受理されること。`pytest tests/`
410件全通過。
